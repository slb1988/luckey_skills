# 个人小游戏开发

把一个有趣想法缩成可玩的最小闭环，再用真实试玩决定下一步。此 skill 保存方法与游戏索引，不承载游戏源码。

## 选择游戏与按需加载

| 游戏 | 入口 | 按任务继续读取 |
|---|---|---|
| 《救一笔！》 / `save_one_stroke` | [游戏说明](references/save_one_stroke/README.md) | [关卡创作与验证](references/save_one_stroke/level-authoring.md)；[VPS 发布](references/save_one_stroke/deployment.md) |

- 已知游戏先读对应入口，再只读任务所需 reference；不要把所有游戏上下文一次装入。
- 新游戏先确认名字、目标体验、平台与源码仓库，在 `references/<game-id>/` 增加独立目录及入口索引，共用下面的流程，不另建一套通用 skill。
- 源码、素材、关卡 JSON、Schema 和测试保留在各游戏仓库；reference 指向权威路径，不复制整仓或维护会漂移的格式副本。

## 轻量开发闭环

1. **锁定本轮目标。** 用一句话说明玩家做什么、怎样成功或失败、本轮想验证哪一个趣味点。只追问会改变实现的缺口；确认游戏目录、目标版本、交付范围，区分“设计建议”“实际开发”和“发布”。
2. **先取最小证据。** 读取目标版本必要的项目指令、规则文档与对应测试，批量处理独立查询；不重读未变材料。并行开发中的未完成文件不是已支持机制的证据，不替其他任务修改它们。
3. **先让一小段好玩。** 优先做一个规则、一种互动和一条可验证的成功路径；写出预期的“原来还可以这样”时刻。不要用更多障碍、更窄空间或更少资源代替玩法变化。
4. **按规则创作并实现。** 先区分“已有机制能表达”与“需要新增引擎能力”。前者按同版本文档、Schema、fixtures 生成数据；后者先实现最小机制，并同步其格式契约与测试，不能凭空造 JSON 字段。
5. **用试玩收敛。** 记录玩家实际尝试、困惑与惊喜，把反馈改写成一个可验证假设；每轮只改变主要因果关系。用户不喜欢某条解题思路时换思路，不只是加难。
6. **分层验证。** 跑项目现有的最小相关校验，再检查真实游戏行为；数据合法、模拟通过和用户觉得好玩是不同结论。涉及输入或关卡存取时，验证相应的交互与导入/导出/保存链路；未实际试玩或未执行的测试明确标注。
7. **交付或发布。** 回报改了什么、玩法意图、验证证据、可试玩入口和剩余边界。只有明确要求发布时，按该游戏的发布 reference，把已推送版本交给目标机 agent；不顺带调整其他站点或部署基础设施。

## 输出与知识边界

- 默认给简短结论、修改路径、实际运行的检查及其结果；有阻塞就说清下一步，不生成“全部通过”的占位报告。
- 稳定方法留在本入口，游戏专属定位与约束留在其 reference。临时进度、当前 commit、关卡数量和某轮测试流水账留在任务回报，不写成长期知识。
- [待确认评测提示](evals/evals.json) 覆盖新游戏、关卡创作和发布交接，仅是候选 prompts；请用户确认后再决定是否执行，本文件不代表行为评测已完成。
