# 最小干预式规则发现小游戏

> 一个可复用的设计抽象：**玩家只做很少的操作，让一个可观察的系统运行，再通过新规则带来的反例，发现更聪明的解法。**
>
> 核心公式：**最小干预 × 可视化系统演化 × 规则发现 × 低成本重试**。

这里的名称是设计工作标签，不是严格的行业分类。物理题材可以归入 physics puzzle / drawing puzzle；但这套模型不必画画，也不必使用刚体物理。

## 1. 到底在抽象什么

《救一笔！》的表层是“画一笔救椅子”，真正可复用的是：

- **熟悉的情境**让玩家先产生直觉：椅子需要腿，东西会往下掉。
- **很小的干预权限**让入门简单：只能补一笔，而不是操作一套复杂编辑器。
- **系统真的响应干预**：画在哪里、连接什么、承受什么力，都会改变结果。
- **新的条件推翻旧解法的适用范围**：能撑住不代表能抗侧推；当前能用的支点不一定一直存在。
- **失败可解释、重试便宜**，玩家愿意马上试另一种办法。

玩家获得的主要奖励不是“我手速更快”，而是：**“原来我刚才把规则理解窄了。”**

### 与参考赛马游戏的关系

两者共享一个外层体验：**低门槛创作 → 作品动起来 → 短局反馈 → 再试或分享**，但核心挑战不同。

| 方向 | 主要挑战 | 创作的作用 |
|---|---|---|
| 涂鸦驱动的社交竞速，如 Doodle Derby | 节奏操作、成绩挑战与个性表达 | 让选手独特、结果有梗；不能未经验证就假定画法决定性能 |
| 创作驱动的规则解谜，如《救一笔！》 | 理解因果、设计干预、发现替代解法 | 玩家创作的结构实际参与系统判定 |

因此，“随便画个东西，再让它跑起来”不足以定义这里的解谜类型；**画法是否有可解释的作用**才是关键区别。

## 2. 标准游玩循环

```text
看懂目标和本关条件
    ↓
形成一个直觉解法
    ↓
做一次有限干预：画 / 放 / 切 / 转 / 连
    ↓
启动短时模拟或系统演化
    ↓
看清成功或失败的原因
    ↓
修正理解，立即重试
    ↓
遇到下一种规则变化
```

“最小”指操作门槛低，不代表思考空间小。一笔可以有很多形状，一个物件可以有很多位置。

短局、搞笑文案、回放和分享是增强体验的手段，不是核心机制的替代品。没有分享按钮时，解题本身也应该成立。

## 3. 将设计拆成六个部分

| 部分 | 要回答的问题 | 可替换的内容 |
|---|---|---|
| 情境 | 玩家一眼看见什么问题？ | 快递将摔坏、灯照不到、雨要淋湿人、货物悬在空中 |
| 干预 | 玩家只能改变什么？ | 画一笔、摆一件物品、剪一根绳、旋转一个部件、连接两个端点 |
| 系统 | 干预以后，世界如何运行？ | 刚体运动、水流、光路、绳索、输送带、离散信号传播 |
| 条件 | 这关哪条假设不能照搬？ | 支点会撤走、作用方向改变、连接可以转动、物体会反弹 |
| 目标 | 怎样才算成功？ | 稳住、送达、保护、导走、点亮、隔离；同时明确失败条件 |
| 反馈 | 玩家如何知道为什么？ | 接触点、运动轨迹、受力方向、事件倒计时、简短因果说明 |

主题主要负责吸引人；**干预方式、系统和规则变化**决定是不是一款不同的游戏。

## 4. 难度要区分三种

| 难度 | 做法 | 适合承担的角色 |
|---|---|---|
| 参数难度 | 墨水更少、缝更窄、负载更重 | 熟练练习、可选三星挑战 |
| 组合难度 | 两个已经学过的条件同时出现 | 巩固和迁移已有理解 |
| 认知难度 | 一个原本好用的假设不再成立，需要换思路 | 新章节的惊喜和记忆点 |

参数变化不是坏设计，但连续用它代替新机制，会让玩家觉得只是在做更麻烦的旧题。

### 什么样的变化算“新的理解”

| 原先容易形成的假设 | 新条件 | 值得发现的解法方向 |
|---|---|---|
| 静止时撑得住就够了 | 先后出现不同方向的推力 | 考虑全过程和两侧稳定，而非只救一个方向 |
| 安全支点可以一直依赖 | 支点在明确预告后撤走 | 设计撤走后的支撑路径，不只检查开局 |
| 连到固定位置就不会动 | 连接是可以转动的铰接 | 区分位置约束与旋转约束，利用重心和悬挂 |
| 承重只需要处理“下面” | 重力方向改变 | 按新的作用方向重新理解支撑 |
| 挡住来物就是最好的保护 | 接住冲击会让结构失稳 | 引导或卸掉冲击，而不是一味硬接 |

这些例子借鉴《救一笔！》的机制，但可迁移到其他题材。不要把关号、具体坐标或某一个标准解写成通用设计规律。

## 5. 惊喜必须公平

**惊喜来自对规则的新理解，不来自系统偷偷换答案。**

- 新条件在试跑前可读；定时变化有清楚的倒计时、方向或状态提示。
- 保留足够多的旧规则，让玩家能迁移已有经验。初次介绍新机制时，不同时塞进一堆陌生条件。
- 失败之后能定位原因，避免只显示“挑战失败”。搞笑反馈可以有，但不能盖过因果信息。
- 接受规则允许的非预设解；不要通过匹配参考笔画或几个神秘像素来决定胜负。
- 尽量给触摸输入和模拟误差留下容差，不把本应考思路的关卡变成精确描线。
- 不强求每关都破例。穿插掌握、组合和轻松关，避免规则多到无法形成稳定理解。

建议的节奏是：**建立直觉 → 熟练使用 → 遇到反例 → 迁移理解 → 组合运用**，而不是永久单调加难。

## 6. 如何生成不同的新游戏

生成概念时，至少改变“干预方式、演化系统、成功目标”中的两项；不要只把椅子换成另一种皮肤。

以下是设计方向，不是《救一笔！》现有引擎的能力声明：

| 概念 | 最小干预 | 核心系统 | 可制造的认知转折 |
|---|---|---|---|
| 《借我一束光》 | 只摆一面镜子 | 可视化光路 | 不能直接照到目标；遮挡有时也能避免照亮错误目标 |
| 《这份快递别碎》 | 只放一个保护物 | 下落、碰撞与缓冲 | 弹得高不等于保护得好；有时应该导向安全落点 |
| 《这一剪有点用》 | 只剪一根绳 | 悬挂物与张力变化 | 先释放配重，反而可以保护目标物 |
| 《这雨怎么横着下》 | 只画一道遮挡 | 雨滴、风和汇流 | 屋顶不只是挡雨，还可能把水集中到错误位置 |

决定实现哪款之后，先选能稳定模拟的最小机制。水流、绳索和复杂材料可能比简单刚体贵得多，不能只因概念表里写了就宣称容易实现。

## 7. 一关的设计卡

先写设计卡，再写运行数据：

```text
目标体验：玩家想完成什么？
已学会的规则：这一关假定玩家已经知道什么？
本关唯一主要变化：哪条条件改变了？
直觉解法：玩家可能先怎么做？
它为什么失效：失败是否真的由本关新机制导致？
发现时刻：玩家应形成什么新的理解？
成功策略：至少一种可解释的合法解法。
替代空间：还有哪些不同的干预可能成立？
提示方式：先提示观察什么，再提示可以怎样想。
验收方式：怎样验证规则、成功路径和有意义的失败例？
```

“直觉解法”是设计假设，不是对所有玩家的预测。用试玩判断玩家实际如何理解，再决定要不要改题。

## 8. 数据驱动与 LLM 的边界

为了支持离线迭代和 LLM 出题，把关卡做成**声明式数据**，但不要发明一个所有游戏共用的万能 JSON 协议。

每个游戏的契约分别说明：

- 对象与初始状态、可用交互、资源限制。
- 已实现的规则、时间事件及其参数范围。
- 成功与失败条件、提示和展示信息。
- 格式版本、导入限制，以及与关卡清单的关联方式。

设计卡、参考解和测试用例可以单独保存；不必把答案塞进玩家下载的运行关卡。

### 必须分开的三种结论

1. **格式合法**：字段、数值、版本满足校验。
2. **行为成立**：同一套运行逻辑下，成功例能过，失败例确实因目标机制失败。
3. **体验有趣**：玩家能理解并感到发现了东西，需要真实试玩反馈。

前两项通过，不能自动证明第三项。

LLM 可以组合已实现的规则，不能仅靠增加 JSON 字段创造引擎能力。遇到新机制，先实现运行时，再同步 Schema、文档和测试；不要放宽校验来接受不存在的能力。

外部关卡只作为数据读取，不执行其中的脚本。采用有限的数值、对象数量、文件大小和模拟时长，避免一次生成把小游戏变成无界计算。

## 9. 最小验证与停止条件

- 一个合法成功例，以及一个能体现新机制的朴素失败例，均使用游戏本身的逻辑验证。
- 必要时做一个机制开/关的对照，确认结果变化来自设计中的规则，而不是偶然的抖动或时序错误。
- 涉及新操作时，在目标设备上验证实际输入；涉及序列化时，验证导入、试玩和导出的闭环。
- 确认反馈能够解释发生了什么；趣味性留给玩家评价，不伪造“玩家觉得惊喜”的结论。
- 有了决定性证据就交付试玩，不为一关扩展全规则组合矩阵、排行榜、账号或在线生成平台。

## 10. 可复用的生成提示词

### 构思新游戏

```text
请设计一款“最小干预式规则发现小游戏”。
目标平台：【浏览器 / 手机等】
受众与单局预期：【填写】
实现约束：【填写技术、资源、是否已有引擎】

核心是：操作少、系统因果可见、失败可解释、低成本重试；
通过规则变化带来“原来还能这样”的发现，不靠一直缩资源或堆障碍。

先给3个不同方向，不要都变成画线救物或给椅子换皮。
每个方向说明：熟悉情境、唯一主要操作、演化系统、成功目标、
玩家最初的直觉、一个推翻其适用范围的变种、最小可玩原型与实现难点。
区分设计设想和已有技术能力。最后推荐一个，解释为什么值得先试。
当前只要设计，不自动写代码或发布。
```

### 给已有游戏创作变体关

```text
为【游戏】设计【数量】个规则发现型变体关。
先读取目标版本的规则文档、Schema、有效关卡和测试用例。
逐关写出：已学规则 → 新条件 → 朴素失败 → 新理解 → 合法策略。

优先使用已有机制，单关只引入一个主要变化；条件提前可见，允许非预设解。
不要把更窄、更重、墨水更少当成唯一的新意。
可表达的关卡按真实契约输出独立文件和相应验证用例；
需要新引擎能力的想法单列，不伪装成可直接导入的数据。
如要求实际执行验证，使用游戏同一套逻辑；如未执行，明确标记“未验证”。
不要自动上线。
```
