# 关卡创作与验证

## 先匹配版本，再生成 JSON

关卡以独立 JSON 配合清单组织，游戏支持单关导入、导出与本地保存。本页只说明创作流程，不维护完整 Schema、字段表或脱离版本的示例关卡。

在目标游戏仓库按下列顺序读取必要材料，所有材料与待运行的游戏必须来自同一版本：

| 权威来源（相对游戏仓库根目录） | 用途 |
|---|---|
| [`docs/LEVEL_FORMAT.md`](https://github.com/slb1988/save_one_stroke/blob/master/docs/LEVEL_FORMAT.md) | 确认格式版本、字段语义、单位、规则约束、导入与清单约定 |
| [`schemas/`](https://github.com/slb1988/save_one_stroke/tree/master/schemas) | 找到该版本文档或校验器实际引用的 Schema，确定必填、类型与取值范围 |
| [`tests/`](https://github.com/slb1988/save_one_stroke/tree/master/tests) 下匹配的 fixtures 与用例 | 找最接近目标机制的有效 JSON、无效边界与 cases 形状；按实际引用定位，不猜文件名 |
| `package.json` 及上述文档指向的校验器 | 确认可用命令、退出状态与 JSON 报告含义 |

生成前先确认用户要单关导入文件，还是要改仓库中的正式关卡与清单。以最近的有效 fixture 为起点，依据文档和 Schema 修改必要字段；不把创意名称擅自当作已存在的机制或属性。

若文档、Schema、实现或 fixtures 不一致，报告冲突并定位目标版本支持的事实；不要通过放宽校验器来掩盖错误。需要新增规则时，把运行时支持、格式文档、Schema 与对应测试作为同一最小改动交付。

## 创作一关

1. 写下一个核心因果变化、玩家可能的直觉解法，以及值得发现的替代解法。
2. 用已有机制检查可表达性；优先制造新理解，而不是重复堆障碍或收紧墨水。
3. 按同版本 fixture 创作独立 JSON；标识、坐标、数值、资源限制与清单关联全部遵循权威契约，不在此预设字段。
4. 验证最小成功路径与一个有意义的失败/边界情形。只有仓库已支持的 cases 格式才能传给校验器。
5. 在真实页面验证相关玩法；若涉及单关存取，检查导入后能玩、导出后可重新导入、本地保存再加载保持语义。正式入库时再检查清单可发现该关卡。

## 校验入口

在目标游戏仓库执行，路径换成实际文件：

```bash
npm run level:validate -- <level.json> --json
npm run level:validate -- <level.json> --cases <cases.json> --json
```

不带 `--cases` 的运行与带 cases 的运行各自覆盖什么，以该版本报告和校验器为准；不要把未提供的 cases 说成已测，也不要把合法 JSON 等同于关卡可解。

保留实际命令、退出码与报告的关键结论；再说明是否做过浏览器试玩、使用了什么输入或解法。未试玩只报告数据/工具检查结果，趣味性仍待用户反馈。
