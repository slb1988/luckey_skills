# analysis.md — 精读方法与产物标准

## 精读策略

一天去重后通常 300-700 个会话，不可能全读。按 `index.tsv`（或话题索引）**从大到小**过：

1. >100K 的会话全读（通常 10-25 个/天）；
2. 50-100K 的按话题索引里的人类提问判断，挑技术排障/方案设计类；
3. 小文件只在话题明显独特时看。

读法：先看 `session_read.py --user` 的人类提问判断主题，有价值再用 `--assistant --tail 4000` 读结论段。**assistant 的最后几段通常就是结论**（总结/修复报告/待办），中间过程不用细读。不够再往前翻。

## 经验条目的质量标准

**收**：
- 可操作的机制/根因（"SetCollisionEnabled 不派发 EndOverlap，要显式 UpdateOverlaps"）
- 排查路径与硬条件清单（"校验器不生效按这 5 条查"）
- 反直觉的坑与假警报（"Python 属性名 phase_data ≠ C++ 名 PhaseDataAsset"）
- 量化结论与参数（"湿身扣 13% 上限，配表按 43.5 算"）
- 可复用的方法/结构（"三级增量判定：stat → MD5 → 重导"）

**不收**：
- 纯任务流水账（"今天改了某文件"无普适价值）
- 大段对话原文（隐私 + 噪音）
- 已有公开文档一句话能查到的常识
- 一次性的临时状态（"CL 123591 待提交"这类很快过期的信息，除非它承载方法论）

**写法**：
- 每条带**来源成员名**（`—— xuzhiyang`），方便回溯找人；
- 相关 CL 号、资产路径、类名保留（团队内部可检索）；
- 一个条目聚焦一个知识点，标题即结论。

## 连续蒸馏的进度管理

- 目录里每个日期一个文件即天然进度表；蒸新一天前 `ls ~/llm-distill/` 确认接续点。
- 方向固定为**从旧往新**（最老可用日期优先），因为 30 天窗口在不断吞噬旧数据。
- 在产物目录维护一个 `README.md` 索引（可选）：列出已蒸日期、经验条数、跳过日期及原因（空壳/无 UE 内容）。

## 层2：每人当天工作详录

文件：`~/llm-distill/<YYYY-MM-DD>/<key_name>.md`

定位：层1 经验条目的**证据链**。读者通过它判断某条经验是通用规律还是特定 case、值不值得复用。所以原则是**事无巨细、保留完整过程**——包括目标、中间走的弯路、假警报、返工，而不只是最终结论。

**详细程度要求**（避免写成摘要）：
- 活跃人员的文件应写到 **100-300 行**；每个工作项的过程链 5-15 个步骤是常态；
- 保留**关键原文细节**：具体命令、参数、坐标、数值、CL 号、文件名行号、报错原文、耗时——这些是后来人判断可信度和复现的依据；
- 长会话按工作项拆分，同一项跨天的承接关系注明（"承接 08-12"）。

**核心写法：信息流转的精炼叙事（2026-08-21 起，取代附录堆砌）**

每个工作项必须讲清**前因后果的因果链**，这是本目录的灵魂：

1. **前因**：为什么要做这件事——谁提的、什么现象/需求触发的、之前卡在哪；
2. **思维链**：关键的推理/决策过程——考虑过什么方案、为什么排除、哪条证据改变了方向、哪里有精彩的假设跳跃（这也是层1「🧠 思维链精选」的素材源）；
3. **设计与修改的因果**：改了什么、**为什么这么改**、这么改会引起什么（影响面/副作用/谁要注意）；
4. **后果**：结果、验证方式、遗留给谁。

**不要做的**：
- 不要把"用户问了什么"逐条罗列（问题清单不是叙事）——用户的提问要织进因果链里，只保留改变了方向的关键原话；
- 不要会话清单附录式堆砌（2026-08-20 版已验证效果差，`person_appendix.py` 仅保留为可选的深挖工具）；
- 不要为了凑行数写流水账——没信息量的会话合并一句带过。

**多会话的覆盖**：同一人的多个实质会话按工作项组织（一个工作项可能跨多个会话），不是按会话罗列；机器人/碎片会话仍合并一句。

模板：

```markdown
# <key_name> · <YYYY-MM-DD>

> 当天 N 个会话（正文完整 M 个），总输入 ~XM tokens。
> 一句话状态：例「整天在调打包版冒烟测试脚本」/「仅机器人流量」/「正文已全部被清理」

## 工作 1：<主题>
- **目标**：...
- **过程**：<按时间/轮次的过程链，含弯路与转折>
- **结论/产出**：...
- **遗留/待办**：...
- **→ 可提取经验**：<哪条进了层1；若判断为特定 case 不值得提取，写明理由>

## 工作 2：...
```

写法要点：
- 过程链用「现象 → 假设 → 验证 → 修正」的叙事，保留关键数据（坐标、数值、CL 号、耗时）——这些是后来人判断可信度的依据；
- 机器人流量合并一段略写（「另有 N 个 skill 抽取 sub-agent 会话，属自动化管线」），不逐条展开；
- 正文全空壳的人也要建档，注明「当日 N 次请求已全部被保留策略清理，仅剩元数据：X tokens」；
- 文件结尾不用写总结陈词，最后一项工作写完即止。

## 思维链精选

留档里约 3/4 的请求带 thinking 块（提取后以 `[thinking]` 前缀出现在 transcript 的 assistant 块里，`session_read.py --thinking` 可单抽）。发现**思路本身值得学习**的片段时单独标记收录。

**什么算"精彩"**（满足一条即可）：
- 假设链漂亮：从矛盾现象直接推出隐藏机制（例：从"普通游泳不掉体力"反推出 Phase GE 拿不到 Ability 对象）
- 验证手段四两拨千斤：用一个便宜实验代替大工程（例：基线后立刻重跑增量验证 9583/9583 全 skip）
- 自我纠错有价值：发现自己的假警报/实现缺陷并给出根因（例：发现 MD5 被提到必经路径使 mtime 快速路形同虚设）
- 拆解方式可迁移：把大问题切成可独立验证的小断言逐个击破

**不收**：中规中矩的逐步执行、纯搜代码过程、堆叠试错的乱撞。

**格式**：思维链条目收在两个位置——
- 层2 对应工作项内嵌 `> 🧠 思路亮点：<一段话概括为什么精彩>` 标注；
- 层1 末尾设 `## 🧠 思维链精选` 节，每条：标题（思路一句话）+ 摘录/复述核心推理 + `—— 来源成员，见 DAY/<成员>.md`。摘录可做必要精简，但保留原始推理结构，不要改写成结论体。

## 层1↔层2 的回链

- 层1 条目末尾的 `—— 来源成员` 即指向 `DAY/<成员>.md`；
- 层2 每项工作的「→ 可提取经验」指向层1 条目编号，或注明「特定 case，未提取（理由）」。
