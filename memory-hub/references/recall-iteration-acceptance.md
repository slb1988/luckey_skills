# Memory Hub 召回迭代验收方法（复盘用）

本文整理 2026-10-27 召回质量迭代（R1～R7）中实际使用的验收思路、判据和工具。迭代内容与台账见
ObsidianVault `.claude/plans/MemoryHub召回质量迭代路线.md`。

## 1. 总原则

1. **先量化，再下结论。** 任何方案都先在本机审计全量数据上统计，不以单个样本推断。
   原锚点修复方案（A+C）就是从单个样本推出来的，回放后只能救回 47 条中的 3 条。
2. **先定判据，再跑实验。** 阈值写进计划后再看结果；结果压线时补充证据，不事后改判据。
3. **一次只改一项，其余作为护栏。** 每项改动单独 commit、单独验收，台账按版本追加。
4. **能离线回放的绝不先上线。** 确定性逻辑（渲染、门禁、压制）用历史审计重放；
   LLM 行为（prompt、输出契约）用同一候选池做 A/B。
5. **歧义时看原文。** 指标只能说明「变了」，判断「变好还是变坏」必须拉出候选原文逐条核对。
6. **口径要干净。** 先剔除评测流量，以及本来就不会注入的候选（无证据、无槽位），再算损失。
7. **默认可回退。** 有行为风险的改动用开关上线，默认关；回退路径写进计划。

## 2. 按改动类型的验收流程

### 2.1 确定性渲染（R1 去流水账、R1.1 标题合并、R1.2 补句）

1. 用工作区代码重渲染本机审计：`scripts/rerender_recall_audits.py --since <日期>`。
   - 读取每份审计中的 `stage_b.items`，与当时实际注入的正文对比。
2. 看四个指标：近重复文件数、套话文件数、字符数、**疑似丢失内容句**。
3. 疑似丢失句逐条用 `--show <审计文件>` 核对。
   - 已知误报：合并后断句变化，内容仍在。
   - 真丢失：先修，不接受。本轮先后抓到三类真丢失：
     - 因果子句被吞；
     - 数值（15.6s / 270 包 / 47ms）被吞；
     - 带文件名的子句被误判为已覆盖。
4. 修复手段要有原理：
   - 「答案原子」护栏：数字、标识符、路径不得因合并丢失；
   - 子句级覆盖：只补未覆盖的子句；
   - 跨分类不改写：related 文本不能借合并升格为已确认。
5. 单测锁定行为，并更新 API 文档里的格式说明。

### 2.2 门禁规则（R3a 锚点核验）

1. 导出击杀案例：`recall_audit_stats.py --export-cases`。必须保留**完整** query、evidence 和 task_relevance。
2. 逐条标注 `useful / correct_kill / unclear`。
   - 坑：首轮按截断到 600 字的证据标注，误标了 1 条。导出时不得截断。
3. 交叉表「标注 × 失败侧（任务侧 / 证据侧）」，找出真正起拦截作用的一侧。
   - 结论：只败在任务侧的全是有用线索；该杀的全部由证据侧拦下。
4. 在标注集上回放候选规则。判据：**correct_kill 零放行**，useful 放行数最大化。
5. 标注集固化为回归测试：`tests/eval/recall-gate-cases.anchor.jsonl` + `test_recall_gate_cases.py`。
6. 余量太小的放宽不做。证据侧放到 0.6 能多救 3 条，但离最近的 correct_kill（0.579）太近，暂缓。

### 2.3 服务端压制逻辑（R2 SUPERSEDES）

1. 先修正口径：总清零 73 次，其中 41 次是无证据候选，**有用候选清零只有 32 次**。
   早期报的「198 次」是口径错误。
2. 按原因分类：
   - 旧引文无法定位：17；
   - 替代者覆盖了全部槽位：6；
   - 替代者不在候选池：9。
3. 顺着代码路径找根因：approved 层旧引文被置空，部分保留因此永不生效。
   能用代码证实的先证实，不能证实的写成假设，并加审计字段等线上数据。
4. 安全边界不动：定位器只用于匹配，从判分载荷中剔除，不进模型。
5. 审计新增 `superseded_reason`。上线后按原因统计，再决定下一步（R2b 待数据）。

### 2.4 Prompt 与输出契约（R5 压缩输出）

1. **拆解成本**：线上拟合 judge 延迟 ≈ 12.1s + 14.2ms × 输出 token，再拆输出构成，找最大头。
2. **开关上线**：`RETRIEVAL_STAGE_A_COMPACT_REJECTS` 默认关；解析器同时兼容两种格式。
3. **A/B 设计**（`scripts/ab_stage_a_wire.py`）：
   - 真实 query：从本机审计按 project 轮流抽取，固化为 `tests/eval/stage-a-wire-cases.jsonl`；
   - 同一候选池（只读拉取一次）；full / compact 交替先后，各 k=3 次；
   - 以 full↔full 的重复一致性作为噪声基准。
4. **预设判据**：
   - 输出 token 下降 ≥25%；
   - 重试不增加；
   - 放行集一致性 ≥ 噪声基准 −0.05。
5. **一致性压线时**看方向（`--analyze`）：是系统性少放（only-full ≫ only-compact），还是换放。
6. **方向偏斜时拉候选原文**判断是噪声还是证据。
   - 第一轮：compact 多拒的都在尾部 rank 4～10，其中 8/11 是真证据。
   - 根因：「0 分不必输出」去掉了逐条作答的清单效应。
   - 修复：要求 r0 显式列出，judgments / r1 / r0 恰好覆盖全部候选。
7. **第二轮复测**：方向对称（8 vs 9），`ranks_omitted` 为 0。
   **有条件开启**：本轮 token 仍降 ≥20%，且延迟更低。
8. **回退**：删除开关并重启，不用回滚代码。
9. **上线验收（10-27 已开启，`a2aa8fe`）**：两次真实召回 rank 全覆盖、无格式重试，Stage A 8.8s / 13.4s。
   - 输出 token 567 / 589，高于原先估的 400～450；
   - 但这两次各有 4～5 个高分候选，同条件下 full 格式的 p50 是 773～819（审计 n=46），实际降约 27%，与 A/B 一致。
   - **教训**：token 预期必须按「高分候选数」分层对比，不能拿全体中位数去比单次召回。

### 2.5 可用性（R7 resolver 降级）

1. 从客户端 trace 统计 503 错误码：近 7 天约 5% 的召回全空。
2. 区分主路径失败与旁路失败。resolver 是并行推测的旁路，它失败不该清空全部召回。
3. 降级设计必须保留原安全属性：未经裁决的争议备选不注入。
4. **用生产失败形态写测试**（judge 偏爱旧答案、纠正只给 1 分）。
   - 首版规则「只看放行的纠错」在这个测试里暴露漏洞，改为不看评分；
   - 再补上压缩输出 r1 无槽位信息时的保守分支。

## 3. 通用测试与上线检查

| 步骤 | 做法 | 注意 |
|---|---|---|
| 单测 | 相关子集 `-k "retrieval or recall or ..."` 先跑 | 新行为必须有测试锁定，改旧断言要说明是有意改变 |
| 全量 | `tests/unit`（排除 Windows 不可用的 `test_agent_integration.py`） | 本机已知 6 个 Windows 环境失败（fcntl、跨进程 SQLite 锁），用 `git stash` 对比基线确认不是新引入的 |
| 偶发失败 | 单独跑、整文件跑都通过即判时序抖动 | 例：`approx(110.0, abs=0.05)` 在全量负载下超时 |
| 客户端 | `scripts/tests`，同样用改前/改后失败清单 diff | 本机 26 个环境相关失败，改前后一致 |
| 部署后 | 跑一次真实召回抽查格式与审计字段 | `memory_hook.py search ... --project <id> --json`，注意 project scope |
| 线上观测 | `recall-metrics.jsonl` + `recall_audit_stats.py --metrics` | 失败率只能从 metrics 看，md 审计只记成功的召回 |
| 台账 | 部署满 ≥3 天，按同口径追加一行 | 护栏任一恶化 >10% 就回退 |

## 4. 工具清单

| 工具 | 位置 | 用途 |
|---|---|---|
| `recall_audit_stats.py` | skill `scripts/` | 审计基线报告、台账行；`--hub-src` 拆锚点失败侧；`--export-cases` 导出击杀案例；`--metrics` 汇总每次召回指标 |
| `recall-metrics.jsonl` | `~/.local/state/memory-hub-hook/` | 每次召回一行（含失败）：origin、错误码、judge 耗时与 token、清零原因、锚点降级 |
| `rerender_recall_audits.py` | memory-hub `scripts/` | 渲染改动的离线验收：去重 / 套话 / 疑似丢失句；`--show` 看单个文件新旧对比 |
| `ab_stage_a_wire.py` | memory-hub `scripts/` | Stage A 输出契约 A/B；`--export-cases`、`--cases-file`、`--use-retrieval-settings`（NAS）、`--analyze` |
| `test_recall_gate_cases.py` | memory-hub `tests/unit/` | 锚点门禁标注回归：correct_kill 零放行，useful 放行数有下限 |
| `MEMORY_HUB_RECALL_ORIGIN` | 环境变量 | 评测流量标记为 eval，与真实交互分开统计 |

## 5. 协作分工

1. **本机**：实现、离线回放、单测和全量测试；commit + push。
2. **@nas**：部署（pull 前先备份 DB），以及需要判分模型 key 的 A/B（key 只在 NAS 的 `.env`）。
3. **结果回传**：至少回传脚本 summary 原文、`--analyze` 输出和方向不一致的 case 明细。
   缺 token / 延迟 summary 时，只能有条件放行。
4. **回传后判定**：按预设判据给出开启、暂缓或改进，写回路线文档。

## 6. 本轮复盘要点（被数据推翻的假设）

| 原假设 | 数据结论 | 教训 |
|---|---|---|
| 锚点近失靠放宽 task 阈值（0.6）解决 | 47 条中只救 3 条；证据侧失败更多 | 单样本不能定方案，先做失败侧分布 |
| SUPERSEDES 一周清零 198 次是主要损失 | 剔除无证据候选后，3 天内有用清零 32 次 | 损失口径要排除本来就不会注入的候选 |
| 召回有 70% 是空注入 | 是评测批量造成的（394 次 / 天） | 评测流量必须排除或打标 |
| shingle 包含度 ≥0.5 即可去重 | 吞掉因果子句和数值 | 合并要有原子护栏和子句覆盖检查 |
| related 与已确认可以同等合并 | related 长文本曾改写已确认行 | 跨分类只做完全覆盖去重 |
| 上线后单次 token 应落在 400～450 | 高分候选多的查询本来就更长；分层对比后降幅与 A/B 一致 | 期望值按条件分层给，不用全局中位数 |
| 压缩输出只省 token、不改判断 | 漏判尾部候选（8/11 是真证据） | 输出格式会改变模型行为，A/B 要看方向并核对原文 |
| resolver 降级只压「放行的纠错」同槽位备选 | 生产形态下纠正常被判 1 分，旧答案照样漏进来 | 降级规则用生产失败形态的测试去打 |

工具使用上的坑：
- Git Bash heredoc 里的 `\\n` / `\\` 转义不可靠，含反斜杠的补丁改用文件或 Edit 工具；
- 临时脚本目录里别用 stdlib 同名文件（`inspect.py` 遮蔽了标准库，导致 numpy 报错）。
