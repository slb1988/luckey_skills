# Codex Review 评审迭代工作流

> 来源：2026-08 memory-hub「入库审核救回（rescue）」特性的实际评审迭代，
> 4 轮评审抓出 3 个真实缺陷（并发竞态 / 配置耐久性 / UX 假成功），修复后清零。

## 何时执行

**仅在用户明确要求评审时执行**（"review 一下" / "评审这些改动" / "入库前检查" 等）。
用户没提评审时不要主动跑——默认流程在 commit 前不做评审。

触发后：用 codex review 评审未提交改动，针对结果重构/修复，再复审，直到无发现为止。
保证进入仓库的是健壮版本，而不是「能跑」的版本。

## 怎么跑

```bash
cd <仓库根目录>
codex exec review --uncommitted        # 评审 staged+unstaged+untracked 改动
```

- **`--uncommitted` 与自定义 PROMPT 互斥**：想加自定义评审重点就不能传
  `--uncommitted`（此时评审默认基线）；评审未提交改动就用裸 `--uncommitted`。
- 其他形态：`--base <branch>`（对分支评审）、`codex exec review -`（stdin 读指令）。
- 本机 codex CLI：`/opt/homebrew/bin/codex`（已登录，无需额外配置）。

## 迭代纪律

1. **每条发现都要修复或显式驳回**（驳回要在 commit message / 文档里留理由）。
2. **每个修复配回归测试**——测试是防止问题回来的唯一守卫。先复现（红），
   修复后转绿。
3. **修完一轮立刻再跑一轮 review**：评审发现是逐轮深入的，第一轮通常抓并发/
   正确性，后面几轮抓配置耐久性、UX 一致性、缓存陈旧等边缘问题；连续一轮
   无发现才视为收敛。
4. 全量回归（不只跑新测试），再 commit & push。
5. 评审反馈里涉及**通用模式**的经验，回填到本文「常见缺陷模式」一节。

## 常见缺陷模式（评审高频命中，开发时自查）

1. **慢调用在途竞态**：「选出候选 → 调外部服务/LLM（慢）→ 事务落库」的模式，
   落库前的状态复查必须覆盖**所有**中途变化路径。只查终态字段（如 decision）
   不够——人在在途期间的组合操作（reject 后又 rescue）会让行恰好回到原状态，
   绕过守卫。守卫要同时校验「仍可被自动处理」的标记。
2. **不要用阈值/计数值当状态**：`attempts == 配置上限` 表达「转人工」会被日后的
   配置调大击穿（旧数据瞬间重新达标）。耐久语义用**持久布尔标记列**，与可配置
   阈值解耦。
3. **批量操作结果统计要穷尽状态空间**：只识别 success/error 两类会漏掉
   not_found / already_processed / memory_deleted 等中间态 → 前端报假成功并
   吞掉混合批次的部分失败。以「动作对应的唯一成功状态」为准，其余一律逐条暴露。
4. **聚合计数驱动的 UI 提示**：任何会改变计数的操作（清空/删除/处置）成功后
   都要刷新聚合来源，否则警示条/角标残留过期数字（轮询关闭时尤其明显）。
5. **SQLite 加列三处同步**：主 DDL + 存量库兼容迁移（ALTER TABLE）+ 测试副本
   DDL；位置式 `INSERT INTO t VALUES (...)` 会随列数变化直接 break，迁移后
   优先全局搜一遍。

## 测试技巧

- **确定性复现在途竞态**：fake LLM/HTTP 客户端的 `complete()` 回调内部执行并发
  操作（如人工 reject+rescue），再返回结果——精确模拟「LLM 在途期间人已处置」。
- pydantic `BaseSettings` 实例可直接属性赋值，测试里临时改配置上限等验证
  配置耐久性语义（fixture 函数级隔离时无泄漏）。
- 协议三方同步类改动（openapi + 后端 + 前端）跑互锁测试（如 test_protocol.py）
  兜底漏边。
