# 最小定位与修复路线

以下仅为待执行方案，未查看源码或执行工程操作。项目专用文件名、AST 类型未知，以下按职责标识入口，不虚构路径。运行测试通过不代表编辑器使用的解析、符号与缓存链路已支持。

1. **先分层定位。** 保留 `async FTask RunAsync(Context T)` 样例，在同一作用域比较 `UISteps::` 与 `await UISteps::`。从大纲、补全提供器逆向追到声明解析、表达式解析、符号收集和作用域解析，查看方法在哪层丢失、补全在哪层中断。通用入口是 `registerDocumentSymbolProvider`、`registerCompletionItemProvider`；若采用 LSP，则查看 `textDocument/documentSymbol`、`textDocument/completion` 的处理器。具体文件须接手时确认。

2. **最小语法修复。** 在函数声明的现有修饰符位置识别上下文式 `async`，记录到函数节点；返回类型沿用原规则，不特判 `FTask`。只有最近所属函数为异步函数时，才按语言约定启用 `await` 前缀表达式；嵌套函数不能盲目继承外层状态。不要将二者全局保留，普通函数里的 `int await` 和作为调用目标的 `await()` 必须仍按标识符解析。补全中的未完成表达式也应保留可用节点和范围。

3. **贯通编辑器消费端。** 确认异步声明仍进入原有函数符号收集路径，大纲得到正确名称、范围与层级，而非另造异步符号管线。补全遇到 await 包装时，应继续解析操作数 `UISteps::`，复用原有命名空间成员查询；先保证作用域和候选可达，不臆加“只显示返回 FTask 的成员”过滤。避免用全局删掉 await 文本的正则补丁。

4. **验证增量失效。** 入口是文档变更处理、函数体解析缓存及语义缓存。只删函数头的 `async` 而正文不变仍出现旧结果，优先检查缓存是否仅以正文或范围判断复用。将所属函数的异步上下文纳入依赖；切换时重建受影响的正文解析、作用域及诊断，并防止旧版本异步结果覆盖新版本。不以重启或清空全库缓存代替修复。

5. **验收证据。** 待实施时提交声明节点与大纲返回值、两种限定名补全的候选对照，以及普通函数中变量名 await、函数调用 await() 的独立回归用例。记录“添加 async→删除→撤销→重做”，每步比较增量结果与同文本冷解析；删除后应按普通函数规则重解释正文，而非要求仍合法。覆盖未完成的 `await UISteps::`，确认无崩溃、旧候选或旧诊断；截图仅作辅助，不声称这些验证已经完成。

**边界：** 本题先限于编辑器解析、符号、补全和相关缓存；没有新证据，不扩大到运行时、编译器、调度器、FTask 实现、全局关键字改造或全项目重构。
